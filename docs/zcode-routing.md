# ZCode routing protocol and qualification

[Z.ai account and route setup](usage.md#zai-coding-plan) · [Configuration](configuration.md) · [Troubleshooting](troubleshooting.md#quota-routing-and-continuation)

This document preserves the dated protocol and qualification evidence. Use the linked usage guide for current operator commands. An observed test result below qualifies that source, client and isolated setup; it does not assert that your installed service or a future provider campaign has the same outcome.

CQ can keep Codex as the agent harness while transporting supported GLM requests through ZCode's account and model services. CQ translates supported Responses requests, tools and tool results to the Messages protocol, then converts JSON or streamed responses back for the caller. This route does not delegate work to the ZCode CLI or start a second agent harness.

The implementation is pinned to **ZCode 3.17.2** and the public source revision [`a9fe401eede6e6e5e01be9048679c206fe6f02d9`](https://github.com/zai-org/ZCode/tree/a9fe401eede6e6e5e01be9048679c206fe6f02d9). The inspected installed `ZCode.app/Contents/Resources/app.asar` has SHA-256 `12a2fc939df2fcb4188699772590f5151f1f2b90556bd34ecb6d44cf0d793cc6`. The installed official build contains request-signing behavior omitted from the public edition. The source pin and installed artifact therefore provide different parts of the protocol evidence; a newer public checkout alone does not establish compatibility with a newer installed build.

Browser login produces several credentials with different purposes. They are not interchangeable:

| Credential | Purpose |
| --- | --- |
| Raw provider OAuth token | Exchanged through the provider's business login endpoint when a business JWT is needed. |
| Business JWT | Reads the account's personal organization/project and key metadata, obtains a Project Access Token, and supplies the business authorization needed by reset-card operations. |
| ZCode JWT | Authenticates ZCode account services, token-plan balances, current offers and claims. It is also the inference credential for Start Plan. |
| Project Access Token (PAT) | Short-lived credential for paid model inference and its signing handshake. It is scoped to the selected account and kept in memory until expiry or invalidation. |

CQ stores browser login material through its encrypted session store. It does not persist PATs, signing key material or CAPTCHA results. PAT resolution selects a real personal organization and project returned by the account service. It reuses the named `zcode-api-key` metadata, creating a normal scoped key only when that entry is absent, then requests an access token. It does not copy an existing key's secret or substitute another account's project. The [pinned PAT contract](https://github.com/zai-org/ZCode/blob/a9fe401eede6e6e5e01be9048679c206fe6f02d9/docs/model-provider-project-access-token.md) describes this distinction between key metadata and short-lived access tokens.

Paid and Start Plan inference use separate routes:

| Route | Endpoint | Authentication |
| --- | --- | --- |
| Paid Coding Plan | `https://zcode.z.ai/api/v1/ultra-zai/anthropic/v1/messages` | PAT in both `Authorization: Bearer …` and `X-Api-Key`; the account's ZCode JWT additionally supplies `X-ZCode-Authorization: Bearer …`. Requests use the normal server-issued signing flow and ZCode 3.17.2 source identity. |
| Start Plan | `https://zcode.z.ai/api/v1/zcode-plan/anthropic/v1/messages` | ZCode JWT in both `Authorization: Bearer …` and `X-Api-Key`. This route does not obtain a paid PAT or run the paid signing handshake. |

For paid routing, CQ obtains signing material from `https://api.z.ai/api/paas/c1f3a7e2/v2/client` using the selected account's credential. It creates fresh request signatures and uses `X-App-Id: zcode`, `X-Client-Version: 3.17.2` and the corresponding ZCode source headers. A URL change alone is insufficient: account authentication, PAT resolution, request signing, source identity and message conversion all participate in the route. Inference is not automatically replayed after an uncertain transport result.

Current claim opportunities come from `GET /api/v1/marketing/touch?seq=…`, with a process-scoped increasing sequence, the logged-in account's device identity, client language, version and ZCode JWT. CQ extracts plan IDs only from current banner or popup buttons whose action type is `claim_zcode_plan`. It preserves the campaign, offered text and public visual arguments for display. It does not infer a claimable plan from static client configuration or the retired `billing/preview` banner. The [current service](https://github.com/zai-org/ZCode/blob/a9fe401eede6e6e5e01be9048679c206fe6f02d9/packages/services/src/marketing-touch/marketingTouchService.ts) and [delivery/action schema](https://github.com/zai-org/ZCode/blob/a9fe401eede6e6e5e01be9048679c206fe6f02d9/packages/shared/src/marketingTouch.ts) define this feed.

A claim requires an explicitly selected current offer, benefit confirmation and a newly completed verification result. CAPTCHA configuration comes from `GET /api/v1/client/configs`, including the current region, prefix and scene ID. A visible loopback browser page loads the official Aliyun CAPTCHA SDK only after the user clicks Verify. The user completes any displayed challenge. The page receives public configuration, never the account JWT. Only an actual SDK result is returned to the pending CQ operation; CQ does not synthesize a verification parameter or reuse an earlier one.

After verification, CQ checks that the same OAuth account and confirmed offer are still current. It records pending intent before sending one `POST /api/v1/zcode-plan/billing/claim` with the selected `plan_id`, the ZCode JWT, `X-Aliyun-Captcha-Verify-Param` and `X-Aliyun-Captcha-Verify-Region`. Success requires code `0`, numeric or string, and a returned plan object. There is no published claim idempotency contract. CQ therefore blocks another submission while an earlier outcome is unresolved and directs the user to inspect the account balance. A saved accepted receipt suppresses duplicate submission; another explicit claim still needs a fresh current offer, confirmation and verification.

Reset-card status, opportunity issuance and card consumption remain separate operations. Status is a read. An explicit opportunity request lets the server decide whether to issue a card and returns its next-attempt cooldown when applicable. An explicit use request selects `FIVE_HOUR` or `WEEK`; the server selects the card within that window type. CQ does not send an exact card ID or promise which individual card will be consumed. Reset operations use the ZCode JWT together with the personal account's business JWT and their documented idempotency key. The [pinned reset contract](https://github.com/zai-org/ZCode/blob/a9fe401eede6e6e5e01be9048679c206fe6f02d9/docs/coding-plan-quota-reset-ui.md) supplies these semantics.

Login, status and offer discovery do not claim token packs, request reset opportunities or consume cards. Reset schedules remain disabled by default; an explicitly reviewed and enabled exact-card schedule can consume its accepted card. Both card-use contracts share an account lock and check each other's unresolved journal before dispatch. The explicitly approved token-plan claim below succeeded. No reset card was issued or consumed during qualification.

Start requests now carry the pinned public product identity and 1,229-character generic identity section, followed by one block containing every caller-owned text instruction in its original order. The generic section comes from the pinned public `identity.ts`; its Apache-2.0 licence is retained and published as a checksummed release asset. The embedded text has an explicit LF checkout rule so its bytes remain identical on Windows. The separate ZCode Desktop visualization instructions and local output directory are excluded from this adapter. Codex still owns the actual tool definitions, tool execution and conversation state. Unsupported non-text system content fails before dispatch instead of being discarded. Paid requests retain their previous projection.

The isolated native qualification deliberately disables Codex request/stream retries. ZCode's [business-error messages](https://github.com/zai-org/ZCode/blob/a9fe401eede6e6e5e01be9048679c206fe6f02d9/packages/ui/src/i18n/locales/en-US.ts) identify codes 3008, 3009 and 3010 as system-busy conditions. These were observed while the account still had available model tokens; accepted requests continued to pass. The adapter does not silently charge paid quota when Start capacity is unavailable.

Local checks passed for the provider and Messages packages with `-race`, native build, `go vet ./...`, Windows/Linux cross-builds and `goreleaser check`. The initial full race run exposed five Homebrew callback fixture failures also reproduced on the clean base. The fixture now loads the generated cask through Homebrew's production `FromPathLoader`, avoiding `FromContentLoader`'s local-variable shadowing during Ruby evaluation. The subsequent full local race suite passed, including unsupported-signature rejection and formatted metadata. Independent review's system-content-loss finding was fixed and its regression passed. These qualification runs used an isolated OAuth profile and local test listeners and left production configuration and service state unchanged.

Final credential-flow review covered account-scoped encrypted storage, OAuth origins and callback replay, project-token scope, request signing and cancellation. Its browser-helper cancellation finding was fixed: synchronous detection commands now follow the verification context, cancellation prevents fallback launch, and an already launched browser remains independent. Helper-process race tests cover Linux and Windows detection, shared macOS helpers, deadlines, child reaping and unchanged private-browser selection. No remaining issue was found in that review scope.

The paid credit measurement matches the combined published multipliers. The [official Coding Plan overview](https://docs.z.ai/devpack/overview) lists GLM-5.3-Flash at **2.3 credits per 10,000 uncached input tokens** and **8 credits per 10,000 output tokens**. For the controlled calls, applying the 50% off-peak rate and the ZCode 0.67 coefficient gives:

```text
Uncached input: 340 × 2.3 / 10,000 × 0.5 × 0.67 = 0.026197 → 0.0262
Output:         79 × 8   / 10,000 × 0.5 × 0.67 = 0.021172 → 0.0212
Total:    (340 × 2.3 + 79 × 8) / 10,000 × 0.5 × 0.67
        = 0.047369 → 0.0474 credits
```

The observed account aggregate matches the exact controlled-call token totals and this calculation. It is billing evidence for those calls, not inspection of the server's promotion predicate. It does not identify which individual request field determines eligibility or establish future campaign terms. The 0.67 coefficient reduces metered credit consumption; it does not add a separate 50% balance. Server-reported offers, balances, cooldowns and accepted receipts remain authoritative for the account.

OpenAI-hosted web search is not a Messages tool. The adapter removes its automatic advertisement only when actual Codex function/custom tools remain, and rejects an explicit unsupported selection. Codex retains ownership of local tools and conversation state. Start-only model discovery uses the public configuration plus the same preferred account's validated token buckets; it neither obtains a paid PAT nor borrows another saved account's entitlements. Public model limits remain unchanged, including the current 1,000,000-token context. The existing GLM-5.3-only 70% compaction policy is applied later against that source's usable context.

PAT renewal and business-token exchange do not renew the underlying browser login. The pinned [Z.ai OAuth adapter](https://github.com/zai-org/ZCode/blob/a9fe401eede6e6e5e01be9048679c206fe6f02d9/packages/services/src/oauth/providers/zaiProviderAdapter.ts) supplies no refresh-token exchange method; the [official service](https://github.com/zai-org/ZCode/blob/a9fe401eede6e6e5e01be9048679c206fe6f02d9/packages/services/src/oauth/oauthService.ts#L999) asks the user to sign in again when that method is unavailable. CQ does not invent an endpoint or promise indefinite login renewal.
